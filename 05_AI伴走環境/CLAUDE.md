# AI伴走環境

## 目的

日置の様々な課題(森信建設・carrire・新規事業など特定プロジェクトに限らない、横断的な課題)に対して、AIが「伴走支援してくれる人」のように機能する環境を設計・構築する場所。特定のプロジェクトの成果物置き場ではなく、AI活用の仕組みそのものを育てる場所。

## 他プロジェクトフォルダとの役割分担

- `03_carrire/`、`01_morinobu-kensetsu/`、`06_新規事業/` などは個別の案件・テーマを扱う場所
- `05_AI伴走環境/` はそれらを横断して支える「AIとの協働の型」を扱う場所

## 発端(2026-08-06)

- 音声会話(ChatGPT)の記録 `会話の確認.pdf`(リポジトリルート)より。社長対応の返信待ち時間を使って、AI活用環境全体を深掘りしようという相談から始まった。
- 話の中で出てきた前提の転換:社長は「何でも自分でやっちゃうタイプ」であるため、こちらから「提案してみましょうか」と持ちかけるより、「社長がやろうとしていることのうち、どこまでなら日置さんの方でやれますか?」と聞く方が合っている、という気づき。

## AI活用環境のレベル設計(たたき台)

一つのチームのように、レベルを分けてAIを動かしていく構想。

- **レベル1**:ライブ会話で思考整理・優先順位付けを手伝う
- **レベル2**:Markdown化して知識として残す
- **レベル3**:GitHubでの資産管理
- **レベル4**:Claude Code / Codex / Gemini などで実際に成果物を作る
- **レベル5**:Google Workspace などの既存業務環境と連携させる

## レベル2の実践:「日置プロフィール」ナレッジベース(2026-08-06)

- ChatGPTプロジェクトに読み込ませ、ライブカンバセーションで伴走支援してくれるAIを育てるため、日置の経歴・課題感・価値観・AIへの期待を切り口別に整理したMarkdown群を `日置プロフィール/` に作成した(レベル2の最初の実践例)。
- **匿名化方針**:ChatGPTという社外サービスに読み込ませる前提のため、実名(会社名・個人名)や具体的な金額は伏せ、構造とそこから得た教訓だけを一般化して残す方針とした。詳細な実名記録(森信建設との交渉経緯等)は`03_carrire/CLAUDE.md`・`01_morinobu-kensetsu/CLAUDE.md`側に残し、外部サービスには渡さない。
- 構成:経歴とスキル/現在の状況(複業構成、スナップショット)/人生目的と価値観/課題感とつまずきパターン/意思決定と交渉のスタイル/コミュニケーション・発信スタイル/AIへの期待、の7つの切り口+索引ファイル。
- 今後の運用:実名記録側(03_carrire/01_morinobu-kensetsu)に新しい出来事が増えるたびに、こちら側への反映(一般化)は都度判断して更新する。特に「現在の状況」は変化が速いため鮮度に注意。

## 運用方針転換:自動メモリ機能をやめ、mdに一元化(2026-08-18)

- Claude Codeにはセッション間で持ち越される自動メモリ機能があるが、使わない方針にした。理由:端末やアプリ(Claude Codeというツール)に依存しない業務環境を構築したいため。学んだこと・決めたことは全てこのリポジトリのmdファイルに残す。
- ルール本体は`../CLAUDE.md`の「ルール」節に記載。
- 旧メモリに入っていた内容をここに移行:
  - 作業が完了したら必ずGitHubにpushする(`../CLAUDE.md`のルールとして既に明文化済み)
  - 日置の学習スタイル:「とりあえずやってみる。間違えたところを繰り返し覚える」タイプ。書籍よりAI・ネットで情報収集する。体系的座学より実践と反復で覚える。AIが学習方法を提案する際は、書籍ベースの体系学習ではなく「まず何をやってみるか」のアクションファーストで提案するのが合っている。

## Codex(音声壁打ち)とClaude Codeの役割分担(2026-08-18)

- 背景:Codex(ChatGPT Plus)を導入。音声チャット機能が優秀なため壁打ち相手として使っている。壁打ちで整理できた内容をPDF出力し、Claude Codeに取り込んでmd化する運用を想定している。
- 役割分担:
  - **Codex**:発散・言語化フェーズ。音声で思考を整理する壁打ち相手(上記レベル設計のレベル1に相当)。
  - **Claude Code**:収束後の構造化作業。ファイル操作、複数mdにまたがる編集、Git管理、プロジェクト横断の文脈把握、実際の成果物作成(レベル2〜4に相当)。

## CodexとClaude Codeを組み合わせた業務フロー(2026-08-18)

1. **Codexで壁打ち**(音声、レベル1)— 思考整理・優先順位付け。実名(会社名・個人名)や具体的な金額は伏せ、構造と教訓を一般化して話す(下記の匿名化方針を参照)
2. **PDF出力** — 話が一段落したタイミングで会話をPDF化
3. **リポジトリに一時配置** — PDFをリポジトリ内(ルート直下 or 該当プロジェクトフォルダ)に一時的に置く。前例:`会話の確認.pdf` → `キャリアOS_音声会話ログ_2026-08-06.md`
4. **Claude Codeでmd化**(レベル2)— 「このPDFを読んで要点をmd化して」と依頼。既存の各プロジェクトCLAUDE.mdや`日置プロフィール/`への反映が必要かも同時に判断する
5. **PDFを削除** — md側にPDFの内容が網羅されていることを確認したら、PDFはリポジトリに残さず削除する
6. **Git管理**(レベル3)— Claude Codeがコミット・push(リポジトリの既存ルール通り)
7. 必要に応じて**Claude Codeで成果物作成**(レベル4)— 資料作成・コード修正など

**決定事項(2026-08-18):**
- **匿名化方針**:Codexにも`日置プロフィール/`と同じ匿名化方針を適用する。外部サービス(Codex=OpenAI)である以上、実名(会社名・個人名)や具体的な金額は伏せて話し、構造とそこから得た教訓だけを一般化して扱う。詳細な実名記録は`03_carrire/CLAUDE.md`・`01_morinobu-kensetsu/CLAUDE.md`側にとどめ、Codexには渡さない。
- **PDFの扱い**:リポジトリに残さない。取り込んでmd化し、内容が網羅されていることを確認した時点で削除する(上記フロー手順5)。

## CodexとClaude Codeの使い分け:4つの観点(2026-08-18)

「片方が書いたコードをもう片方にレビューさせる」等、一般的な組み合わせ方を検討した際の整理。

### ①コードレビューはどちらがやるべきか

本質は「書いたのと同じモデルにレビューさせない」こと。同じモデルは同じ盲点を見逃しやすいため、Codex⇔Claude Codeどちらが書いてどちらがレビューするか自体に固定の優劣はない。あえて言うなら:
- リポジトリ全体を横断して整合性を見る系のレビュー→ファイル直接操作できるClaude Code向き
- 本当に重要な変更は両方に一度ずつレビューさせて突き合わせるのが一番安全(手間は倍)

### ②それぞれの苦手分野

両方とも数ヶ月おきにモデル更新されるため、「Codexはこれが苦手」と断定できる固定知識はない。運用としては、重要なタスクだけ最初の数回は両方に投げて比較し、傾向が見えたらパターン化する、という経験的なやり方が現実的。比較した結果はこのmdに書き残し、判断根拠として蓄積していく。

### ③長時間の自動タスク vs 対話的な微調整

モデル性能差というより、環境の作りに基づく判断。
- **Claude Code**:VSCode拡張内でファイル直接編集・git管理まで完結できるので、長時間の自動タスク(大規模リファクタ、大量ファイル処理)向き
- **Codex**:音声チャットが強みなので、対話的な壁打ち・方針の微調整向き

### ④出力→入力の分業

同じ理由で、上記「業務フロー」の運用(Codex=思考整理→Claude Code=構造化・実装)がそのまま自然な上流→下流の分業になっている。逆方向(Claude Codeの作業結果をCodexの音声で振り返る等)も可能だが、今のところ必然性は薄い。

## 今の使い方における向き不向きの判断(2026-08-18)

このリポジトリの実態は「アプリ開発」ではなく、交渉・経営判断・人生設計・契約実務などの言語化・構造化が中心。その前提で各プロジェクトフォルダの作業をどちらに振るか。

- **Codex向き**(音声で発散させたい、思考整理が主目的の場面):
  - `01_morinobu-kensetsu/` の交渉戦術の壁打ち(次にどう動くか迷っている段階)
  - `03_carrire/` の人生選択の思考整理(答えが決まっていない、話しながら考えたい場面)
  - `06_新規事業/` の初期アイデア出し
  - シンワ技術様との商談前の頭の整理(移動中・隙間時間の音声向き)
- **Claude Code向き**(すでに方向性が決まっていて、構造化・実行・複数ファイル操作が必要な場面):
  - `02_shinwa-tech/` の契約書ドラフト作成、資料PDF化、GitHub共有作業
  - `04_personal-hioki/` の実装作業全般
  - `07_就業規則・賃金規定_勉強/` の学習内容の体系的な整理・記録
  - 各プロジェクトのCLAUDE.md更新、フォルダ構成変更などリポジトリ全体に影響する作業
  - 複数プロジェクトを横断した整合性チェック(今回の番号付けのような作業)
- **判断の軸**:「まだ答えが決まっていない・声に出しながら考えたい」→Codex、「答えは決まっていて、それを形にする・複数ファイルに反映する」→Claude Code
